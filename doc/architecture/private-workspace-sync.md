# Private workspace 元数据本地更新与合并提交

实现位于 `src/workspace_overlay/stores/local_metadata.rs`，作用于 Redis/TiKV
Packed workspace 的应用元数据事务。默认 `remote`，每次等待元数据库确认。
`local-journal` 先同步本地日志，再返回；后台把合并结果写回同一个元数据库。
`local-buffered` 先更新内存，按批次落盘并写回元数据库。

| 模式 | 操作返回时已完成什么 | 未 fsync 的修改 |
|---|---|---|
| `remote`（默认） | 元数据库确认 | 按现有远端持久化语义处理 |
| `local-journal` | 本地日志 fsync | 本地盘保留时可核对日志恢复 |
| `local-buffered` | 本地内存更新 | 进程或机器崩溃时可能丢失 |

三种模式的 fsync 都等待远端确认。逐次落盘有磁盘同步开销，不能把它当成
必然更快的选项；希望省去逐次落盘、接受未 fsync 修改丢失时使用 `local-buffered`。

## 配置

```bash
export BREWFS_METADATA_SYNC=local-journal
export BREWFS_METADATA_JOURNAL_DIR=/local-durable/workspace-123/metadata
export BREWFS_METADATA_FLUSH_MS=10
export BREWFS_METADATA_MAX_OPERATIONS=1024
export BREWFS_METADATA_MAX_BYTES=1048576
# 随后执行原有 brewfs mount 命令。
```

恢复同步模式：`BREWFS_METADATA_SYNC=remote`。切换前必须正常卸载并排空，不能
通过关闭配置忽略遗留日志。日志目录使用本地持久盘，必须在 FUSE 挂载点之外。
每个 workspace 独占目录；文件锁拒绝第二个进程使用同一目录。日志绑定数据库、
namespace 和 workspace 的摘要，不能拿一个 workspace 的日志恢复另一个。

| 参数 | 默认值 | 允许范围 |
|---|---:|---:|
| 后台触发间隔 | 10 ms | 1–1000 ms |
| 每批操作数 | 1024 | 1–4096 |
| 每批元数据键和值的字节数 | 1 MiB | 1 KiB–4 MiB |

最多保留一批正在提交的数据和一批新修改，另有序列化及日志快照的临时内存。
超过条数或字节上限时先提交再接收；单笔过大的事务走原来的同步路径。
后台没有新请求也会触发提交。间隔不是网络故障下的完成时限。
原来的上层读取缓存仍为 65536 项，与待提交队列是两项独立预算。

## 连续修改如何合并

已有事务生成权限检查、inode、目录项、删除标记、extent 和 head 版本。
本实现保留这些检查和完整事务，只把实际远端提交推迟：

1. 校验远端时钟、租约截止时间和本地合并视图中的前置值。
2. 把完整操作写入带校验和的日志快照；文件 fsync、原子替换、目录 fsync。
3. 新视图一次性可见。相同 KV 键只保留最后一次修改，删除值也参与合并。
4. 后台固定当前批次。下一次修改进入新批次，不能改变正在发送的数据。
5. 元数据库 CAS 同时写入元数据、head 和批次确认摘要，再同步本地确认状态。

`local-buffered` 在步骤 2 只更新内存；步骤 4 固定批次时，再对完整批次执行
日志落盘，之后才发送远端事务。两种模式均保留发送前和确认后的日志。
逐次日志模式在落盘期间持有状态锁，保证返回的新视图已经保存。
内存合批模式先固定快照，再释放状态锁执行落盘；新的修改可同时进入下一批。
提交驱动保持串行，取消等待不会中断正在执行的提交或让两次日志写入交叉。
若确认日志落盘失败，即使没有新修改，下一次排空也必须重写确认记录后才能成功。

例如 inode 先改为 v1，提交 v1 时又改成 v2：本地读到 v2；v1 确认只移除 v1
批次。v2 仍待提交。即便 v2 的内容恰好等于 v1，也保留新操作的序号。
远端回复丢失时，读取同一事务写入的确认摘要，判断该批次是否已经完成。
不会重新执行一个结果不明的文件操作。

extent 的区间覆盖仍由现有代码处理，不能把不同区间直接当成一个键覆盖。
只有现有代码生成的相同存储键才合并；序号不同的 extent 保留其顺序。

## 必须等待远端的边界

以下操作排空待提交元数据，再继续：

- 文件 fsync、flush、目录 fsync 和正常卸载。
- 上传完成并释放本地脏数据副本之前。
- ID 分配、租约更新、所有权变更、发布、切层等非应用元数据 CAS。
- 范围扫描和发布证明。

因此目录枚举、数据写入收尾等操作可能提前结束合批。这里保留原有的上传、GC、
发布和范围读取检查，没有把“本地已保存”算成“远端已持久化”。
点读取优先使用新修改，其次使用正在提交的批次，最后读取远端。
普通批量读取保持原有接口；一致读取仍由后端的一致快照保证，不额外查询时钟。
只有要求时钟的读取和修改前校验使用带时钟的接口。
有界读权限验证可将本地 head 还原成批次最初的远端 head，继续校验原有租约和
权限条件；不能还原的检查先排空。它不会为了合批跳过租约或版本验证。

## 失败与恢复

提交失败保留两批数据和日志，后台重试；fsync/卸载返回真实错误。达到队列上限
后不能继续无界接收修改。租约过期或其他写者改变前置条件时，拒绝旧批次写回。

重新打开日志会先尝试完成旧批次，再允许获取新的挂载会话。已提交但未写本地
确认的批次，通过远端确认摘要恢复。**过期租约的未提交日志不会自动换成新租约
重放**；此时挂载失败并保留日志，需要单独恢复流程。不能删除日志强行重挂。

本机和本地盘一起丢失时，尚未远端确认的修改可能丢失。迁移、fork、发布前必须
成功排空；当前实现没有提供“丢弃未同步修改后继续成功”的选项。

## 本地验证

`tools/perf/check_local_metadata.sh NEW_OUTPUT_DIRECTORY` 启动一个仅监听本机的
临时 Redis，轮换顺序测试三种模式，各重复三次，保存逐次耗时和 commandstats，退出时
删除该容器。需要本地已有 `redis:7.2-alpine`，脚本不会拉取镜像或申请云资源。

单元测试覆盖重复修改、旧确认、新批次、确认丢失、重试、重开日志、租约失效、
容量限制、删除标记、空闲后台同步。Packed 集成测试覆盖 chmod、重复覆盖写、
truncate、rename、unlink 以及远端排空。
完整正确性检查使用 `tools/perf/check_hot_overlay.sh`，不能用小测试代替。

设置 `BREWFS_METADATA_PROFILE=1` 可记录合批路径的累计耗时，包括前台等锁、
远端校验、快照序列化、文件 fsync、目录同步、远端事务和确认。真实 Redis 小测试
将各段计数和耗时写入 `LOCAL_SYNC_RESULT.stages`；挂载在正常关闭后输出一行
`BREWFS_METADATA_PROFILE` JSON。默认不计时。各段可能嵌套或并行，不能全部相加；
正式端到端对照关闭该选项，诊断时单独开启。
