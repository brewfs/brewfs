# Private workspace 的本地缓存与后台同步

状态：同步协议设计，尚未实现后台元数据提交。当前实现仍等待远端确认。
本轮热读优化只缓存经过查询的空结果，不改变写入、fsync、发布或迁移语义。

## 模式与承诺

| 模式 | 操作何时返回成功 | 断电后恢复 | 源机器和本地盘一起丢失 |
|---|---|---|---|
| `remote`（默认） | 相关数据对象持久化，远端元数据事务确认 | 从远端恢复 | 已确认操作仍在 |
| `local-journal`（可选，待实现） | 必要数据和元数据日志在本地持久化，本地视图更新 | 日志所在盘还在时重放 | 尚未远端确认的部分可能丢失 |

两种模式都只允许一个租约持有者修改 workspace。同一挂载内，已返回成功的
修改立即可见；其他 agent 通过显式发布的不可变版本共享数据。这里调整的是
写入确认和远端持久化时机，不降低同一 workspace 内 rename、link、unlink 的原子性。
不提供“只放内存就确认成功”的模式。

建议配置接口（尚不接受这些配置）：

```toml
[workspace.sync]
mode = "remote"
flush_interval_ms = 10
max_pending_operations = 1024
max_pending_bytes = 16777216
max_pending_age_ms = 100
journal_directory = "/local-durable/brewfs"
```

间隔是合批触发条件，不是网络故障时仍可保证的远端完成时限。达到条数、字节数、
最老记录年龄上限后，新修改等待同步；后台发生永久错误则返回错误并停止接收写入。
日志空间不足不得静默退成内存确认。配置阈值需校验为非零且有明确上限。
日志目录必须位于挂载点之外的持久化文件系统，按 workspace 和租约代数隔离，
避免写日志再次进入同一个 FUSE 挂载。待同步字节包括元数据日志和它引用的本地数据。

## 本地状态与提交顺序

每个 workspace 维护 `visible_seq`（本地可见）、`journal_seq`（本地已落盘）、
`remote_seq`（远端已确认），以及当前租约代数和远端 head 版本。
已确认的本地操作满足 `remote_seq <= visible_seq <= journal_seq`。
单条日志是完整原子操作；rename 及其两端目录项不能拆成独立可见步骤。

1. 在现有 `mutation_gate` 下生成下一序号和完整变更集，校验权限和当前视图。
2. 写入新数据的本地持久化文件，再写日志。日志包含 workspace、租约代数、序号、
   操作 ID、前序号、原 head、变更集及数据摘要；记录带长度和校验和。
3. 同步本地数据和日志，必要时同步新建文件的父目录。更新本地待提交视图与
   `visible_seq`；失效对应缓存。`local-journal` 此时才返回成功。
4. 后台沿序号合批：先上传不可变数据，再以带 fencing 的 CAS 原子提交元数据、
   操作 ID 和 `remote_seq`。确认应答后推进 `remote_seq`。
5. 远端确认前保留日志及其数据文件。检查点落盘并原子替换后才回收已确认段。

上传中的远端对象需要可恢复的批次保留记录，提交时将它转成正式引用；未确认的
对象不能仅因尚未出现在文件元数据中就被 GC 删除。失败批次在核对日志、租约和
保留期限后再回收；本地日志仍持有的数据允许重新上传。

可以复用现有 `write_queue`、`commit_next_write_batch` 和 `commit_with_written`，
但当前队列仅合并数据写入，且每个调用者都等待远端结果。新增日志必须覆盖目录、
属性、删除和截断；仅提前发送现有 oneshot 应答不构成正确的异步实现。
当前远端协议还需要事务性的操作 ID/序号记录，不能假定其已经支持日志重放。

## 缓存如何看到未同步的修改

读取顺序为：本地待提交修改 → 已确认上层缓存/远端上层 → 不可变 lower。
本地删除标记必须遮住下面两层；本地 hole 与缩短后的 EOF 必须遮住旧数据。
缓存键包含 workspace、租约代数、head/base 身份与版本、inode/目录、查询范围。
缓存的有效性绑定本地可见版本，不能只绑定滞后的 `remote_seq`。

本轮空结果缓存采用现有 65,536 项上限，并复用提交前后失效、版本票据、取消后
永久禁用缓存权限的机制。任何提交令之前的空结果失效；数据或删除标记不放入
空结果缓存。将来接入本地日志时，失效必须移到“本地可见”之前，后台确认后
不能覆盖更新的本地缓存。缓存和日志采用不同容量预算，缓存淘汰不得丢弃待提交操作。

## 强制同步点

- `fsync`/`fdatasync`：捕获调用时的 `visible_seq = S`，等待相关数据上传且
  `remote_seq >= S`。首版保守地排空 workspace 到 S；之后的新写入不延长本次等待。
- 发布、fork、快照：先停止进入发布范围的新修改，排空到 S，再发布远端版本。
- 迁移：源端停止新写入，排空到 S，记录 head/版本/序号并释放租约；目标取得
  新租约并核对 S 后恢复。仅复制 workspace 文件而遗漏日志不算完整迁移。
- 卸载与 `local-journal → remote` 切换：等待相同的远端屏障；失败必须明确返回，
  保留日志。`remote → local-journal` 仅在队列为空、持久化目录已校验时切换。
- 租约失效：停止写入及后台提交，拒绝旧代数继续重放，不自动取得新租约续写。

## 崩溃与不确定应答

部分写入的日志尾部依靠长度/校验和截断；已落盘完整记录才能重放。请求超时后先
查询远端操作 ID 和序号：已应用则只补确认，未应用且原版本仍匹配才重试。
远端版本已由其他持有者推进时，保留日志并报告冲突，不覆盖、不跳过该记录。
新持有者接管旧日志需要显式核对远端 head、已确认序号和完整数据；旧租约凭证
不能直接复用。源盘丢失时恢复边界是 `remote_seq`，必须向调用者说明缺失区间。

## 必需观测与验收

记录 visible/journal/remote 三个序号、待同步字节/条数/最老年龄、合批大小、日志
fsync 时延、远端提交时延、重试数、屏障等待时延、租约拒绝数及最后同步错误。
同步错误必须在 API 和监控中可见，不能只有日志警告。

在提交前、服务端已提交但应答前、本地检查点写到一半、日志回收中分别杀进程；
覆盖本地磁盘满、Redis 断连、对象上传失败、租约转移、重复重放及模式切换。
对每个返回成功的操作检查恢复状态；对每个成功 fsync 检查丢弃本地日志后仍能
仅从远端恢复。比较两种模式的总耗时、fsync P99、实际数据/元数据请求数及恢复时间。
通过这些检查之前，后台元数据提交保持未实现状态，不用于本轮热读收益。
