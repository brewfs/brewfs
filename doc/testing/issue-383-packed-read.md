# Issue 383: packed v3 random-read investigation

Investigation date: 2026-10-30. Source baseline: `80ddaf7`.
The full local report is `/work/REPORT-383.md`; evidence is under
`/work/issue383/` and build/test logs under `/work/logs/issue383-*`.

## Reproduction and scope

The measured environment is 8 vCPU / 30 GiB RAM, TiKV 8.5.0 and RustFS
1.0.4 on loopback. The CPU is Xeon Platinum 8269CY: AVX2 is available,
SHA-NI is unavailable. Both binaries use the same release compiler settings:
`CARGO_INCREMENTAL=0`, `CARGO_PROFILE_RELEASE_DEBUG=0`,
`RUSTFLAGS='-C debuginfo=0'`, and `-j 2`. Build/test jobs run in tmux with
the compose backends stopped; no compilation overlaps measurements.

The four source files each contain a deterministic 4 MiB block generated by
`random.Random(20261029 + i).randbytes(4 << 20)`, repeated 128 times. Source
hashes are in `/work/logs/issue383-corpus-sha256.json`.

Fixture stdout (`/work/issue383/fixture.log`):

```text
packed_version=v3 source_entries=4 unique_inodes=5 groups=1 frames=0
```

The `frames=0` summary counts grouped payload only. The provenance sidecar
`manifest-key.source.json` records 512 external 4 MiB frames in 128 external
16 MiB chunks, all Raw codec, totaling 2 GiB raw/stored bytes.

The exact fio command is:

```bash
fio --name=packed383 --directory=/work/issue383/mnt \
  --rw=randread --bs=4k --size=512m --numjobs=4 --ioengine=libaio \
  --iodepth=32 --direct=1 --runtime=30 --time_based \
  '--filename_format=r.$jobnum' --randseed=20261029 \
  --readonly --group_reporting --output-format=json --output=<run>.fio.json
```

W means two identical 30-second fio warmup passes followed by three measured
30-second passes on the same mount. It does not mean two full corpus sweeps.
The mount uses default 16 FUSE workers / 512 background requests / one Tokio
worker, ordinary read RAM/SSD budgets of 300 MiB / 1 GiB, no cache compression,
no prefetch, and `read_fetch_policy=whole-object`. Packed V3 ownership uses its
separate default mount budget. Each arm uses a fresh empty upper workspace
over the same immutable lower. The repository's lifecycle compose file owns
the TiKV/RustFS services. The Redis perf runner does not support this packed
fio layout, so this is the issue's explicitly requested TiKV/FUSE experiment.

The clean baseline (`before-valid-w`, including successful teardown) measures
127 / 128 / 128 KiB/s and p99 4395.631 / 4328.522 / 4278.190 ms. Each measured
pass has exactly 3.000 GET/read. This reproduces the GET amplification and
severe slowdown, **not** the issue's original 15 KiB/s / 16 s absolute result.
The original remote binary/config and archive were unavailable in this
workspace. The one original-offset EIO was not reproduced.

The candidate W series is 189 / 190 / 188 KiB/s, p99 2936.013 / 2969.567 /
2969.567 ms, with 3.000 GET/read in all three runs and clean teardown. The
candidate median throughput is +47.7% over the baseline median; mean clat and
p99 both fall about 31%. Candidate packet TTFB is 2.355–2.428 ms and complete
body wire time is 6.352–6.509 ms. The separate candidate profile returned fio
`error=5` at two offsets and remains diagnostic only.

## Three GETs, client identity, and latency

Five individual aligned `O_DIRECT` reads were correlated with packet captures
in `before-p1/pread.jsonl` and `before-p1/pread.gets.tsv`. At logical offset
360042496, a successful 4096-byte read takes 36.217 ms and makes:

| Object class | Range | Length | Complete wire duration |
| --- | --- | ---: | ---: |
| GroupMeta | `bytes=4234-4388` | 155 B | 1.382 ms |
| Frame directory | `bytes=0-4431` | 4432 B | 0.648 ms |
| External data frame | `bytes=4198432-8392735` | 4 MiB | 7.106 ms |

These are three authenticated object classes, rather than three fragments of
one data-frame GET. All captured responses are HTTP 206. There are zero new
S3 TCP connections during the measured intervals; the plain HTTP connection
is established during mount. P1 GET TTFB averages 2.285 ms (maximum 11.028 ms).
Responses with complete packet coverage average 8.019 ms of full wire time
(maximum 92.438 ms). Coverage counts are retained; missing response tails are
not reported as complete GET durations.

The production TiKV route is:

```text
VirtualFileSystem::read_packed_workspace_request
  -> WorkspaceMetaLayer / PackedV3ReadonlyMeta::prepare_unified_read_observed
  -> AuthenticatedV3Snapshot::prepare_inode_read_observed
  -> authenticated GroupMeta / frame directory / V3DemandCoordinator
  -> ObjectClient::typed_exact
  -> V3ReadonlyBackend / ReadonlyTransport
  -> shared S3Backend / aws_sdk_s3::Client
```

`brewfs_s3_get_ops_total` and `brewfs_read_range_gets_total` belong to
`ObjectBlockStore`, which this route bypasses. Its whole-object/sparse policy
also does not select packed frame fetches. The zero legacy counters do not
establish a second S3 implementation or a freshly constructed client.

There is an additional observability defect: `src/cli.rs` registers row-cache
stats before packed stats, whereas `FsStats::set_extension` permits only one
registration through `OnceLock`. Thus the existing packed/read-observer
metrics are also missing from this mount's `.stats`. GET counts in this
investigation come from packet capture, not those absent counters.

The CPU profile (`before-profile/perf.data`, 2805 samples, zero lost) places
73.26% of self CPU in `sha2::sha256::compress256`; 73.01% of all samples follow
`V3DemandCoordinator -> fetch_batch -> Sha256::digest(full stored frame)`.
One 4 KiB logical read authenticates 4 MiB, a 1024-fold payload amplification.
On this CPU `sha2` 0.10.9 chooses its scalar software fallback. The profile
accounts for about 22.7 ms hashing CPU per successful logical read.
The demand registry shares only concurrent in-flight owners;
`V3FrameLeader::complete` removes the registry entry before publishing the
result. It is not a retained payload cache. Consequently two fio warmups do
not turn later packed frame reads into ordinary block-cache hits.

Fio clat also includes submission/completion batching effects. The profile
records 916 blocking `io_submit` calls for 916 reads, one IOCB per call, with
mean syscall duration 131.027 ms; fio mean clat is 3800.911 ms. A separate W
diagnostic has mean FUSE read service of 108.71 ms and fio mean clat of
3492.91 ms, approximately the configured depth of 32 times larger. These
measurements explain why fio seconds cannot be interpreted as a single GET
duration. The original exact 16-second result remains unverified.

## Candidate and validation status

The single optimization replaces the SHA-256 computation backend only for
packed wire005 data-frame authentication with the already locked `ring`
0.17.14 implementation. Direct and coalesced frame reads share one helper;
both still authenticate every stored byte and compare the first 16 digest
bytes. Writer and metadata hashing continue using `sha2`. The optional direct
dependency is enabled by `workspace-overlay`.

Standalone diagnostic screening on the same 128 x 4 MiB workload measures
188.32 MiB/s with scalar sha2, 210.35 MiB/s with sha2-asm, and 344.00 MiB/s
with ring, with identical digest bytes. The asm candidate was rejected and
its dependency edits removed before the final build. Screening is not a
filesystem acceptance measurement.

New tests compare known empty/abc SHA-256 vectors and the writer's digest at
padding/block boundaries, misaligned starts, and 4/8 MiB lengths. Existing
corruption, short/trailing-body, follower, and retry assertions remain intact.
The ACL permission TTL and read-fetch defaults are unchanged. Two pre-existing
test statements in `src/config.rs` receive rustfmt-only line wrapping changes.

The required workspace library/binary suite passes: 1275 library tests and
2 CLI tests, zero failed. The required overlay test-count gate also passes:
**2571 passed / 0 failed / 451 ignored**, no filtered tests. The extra two
passes are the new digest compatibility tests. Formatting, shell harness
checks, workspace check/build, and both FUSE runtime checks pass.

Strict workspace/all-target and overlay Clippy also pass; full local CI
completed at 12:12 CST. Paired read guards add 36/36 direct boundary reads and
3x128 metadata rounds on both arms. Baseline sequential reads are 31,030 /
30,883 / 30,635 KiB/s (p99 4.664 / 4.530 / 4.530 s); candidate read-only
guards are 44,625 / 44,430 / 46,434 KiB/s (p99 3.272 / 3.171 / 3.204 s).
The paired mixed-write guard stops in its baseline warmup with fio `error=5`
and repeated FUSE EIO; this is the known packed write/sync defect associated
with #382, so no mixed performance claim is made. All completed mounts tear
down cleanly. No README performance comparison is updated on the strength of
a single focused metric.
