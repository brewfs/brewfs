# BrewFS 根据已定型对象自动选择 RustFS hint

新增显式候选策略 `tiered` 见 [多档对象 hint 策略与资格验收](rustfs-tiered-object-hint.md)。本文的 `auto` 行为及历史测量保持不变。省略 hint 不等于对象全部 inline：当前默认 2+2 普通 PUT 的边界为 256 KiB，版本化时为 32 KiB，MPU 另走外部 part 路径。#362 后可用 `read_fetch_policy` 显式控制 GET/Range 与预取；下文历史“整块读取联动”不代表启用 hint 会覆盖该显式配置。

自动 hint 基于 `codex/rustfs-ec-block-size-hint` 的 `e779c079b4cdcf472645249ab79edd766efce58a`；整块读取联动基于后续 `de77445`，已交付组合为 `e5fec71`。当前实现进一步释放已上传块的写预算、共享缓存热读回复，并根据 ACS 整文件对照修正 auto。下面区分当前策略、最新确认及历史实验，历史 4 MiB auto 数据不代表当前策略。

## 从本地缓存获取可靠大小

写入链路为：文件写入 → 内存块及 SSD writeback 暂存 → 后台 uploader → `ObjectBlockStore::write_fresh_vectored_inner` 补零、压缩、加格式头 → S3 普通或 create-only 上传。恢复的暂存数据也通过块存储上传。

后台可能在文件仍被追加时上传已经定型的数据块。磁盘预分配量、文件当前长度、整个 slice 长度及缓存总占用都不等于最终 S3 对象长度。SSD 暂存是恢复源；选择 hint 时直接使用上传对象的准确字节数，避免扫描 SSD、增加 journal 字段或等待文件关闭。读取不需要重算 hint，RustFS 使用对象已持久化的 EC 布局。

当前写入器同时存在“先暂存再上传”和“暂存、上传并行”的路径，不能假设所有上传都发生在 SSD 写完之后。统一在 S3 入口决策可覆盖两者。一个暂存 slice 也可能拆成多个 S3 对象，hint 必须逐对象选择，不能只对整个暂存文件做一次判断。

## 精简策略

| 配置 | 上传行为 |
|---|---|
| 不配置 | 不发送 hint，保持服务端默认策略 |
| `auto`，最终对象 ≤ 1,048,576 bytes | 不发送 hint，保留小对象默认与内联策略 |
| `auto`，最终对象 > 1,048,576 bytes | 发送 1,048,576 bytes hint |
| 固定 65,536 / 262,144 / 1,048,576 / 4,194,304 | 每个新对象发送指定值，供明确覆盖和对照实验 |

当前策略适用于本轮验证的 4 MiB BrewFS 数据块和整对象工作负载。旧策略对较大对象自动选择 4 MiB EC；相同客户端和服务端的四轮对照没有支持这种选择，且包含明确冷读回退，因此改为明确选择 1 MiB EC。固定 4 MiB 等选项仍供显式覆盖。这里的动态决策是按最终对象大小决定是否提示，并没有改变 BrewFS 的数据块边界，也没有增加未经验证的小块档位或缓存压力调节。

例如，不压缩的 4 MiB BrewFS 块实际为 4 MiB + 4 bytes：按 1 MiB EC 块需 5 段，按 4 MiB EC 块仍需 2 段。段数减少没有在本轮转化为稳定的整条链路收益，不能据此推断吞吐提升。小于等于 1 MiB 的编码对象继续省略 hint，保留服务端默认及内联选择；即使原文件很大，压缩后的小对象也按实际大小处理。

同一上传对象重试的选择稳定；小尾块独立决策；MPU 使用完整对象大小决定创建请求的 hint，而不是某个 part 的大小。普通、vectored、create-only、MPU、vectored MPU 五条路径共用一个选择函数。Cargo feature 默认关闭，未编译却配置 `auto` 或固定值时明确拒绝。

## 整块读取联动

配置 `auto` 或固定 hint 后，BrewFS 将同一冷块的 FUSE 片段读取汇入现有的完整 GET SingleFlight，并直接解析返回对象的帧头。这样一次下载可以覆盖后续片段，省去独立格式头探测和小 Range 与整块预取的重叠传输。完整响应沿用已有解码、长度与完整读取检查。

此模式下，现有 Moka 内存缓存采用 LRU，容量仍由原来的字节预算约束。文件系统会把完整文件读取拆成许多小 FUSE 请求；TinyLFU 中已经读完的旧块会积累访问频率，可能拒绝刚下载的新块，造成后续片段再次下载。LRU 让当前读取流的块进入缓存。未配置 hint 的挂载沿用原来的读取和缓存策略。

该组合面向整文件、整数据块工作负载。ACS 对照使用 4 MiB BrewFS 数据块和 64 MiB 读内存缓存。应用文件大小、实际上传对象大小和 RustFS EC 块大小分别记录；自动 hint 按编码后的对象大小选择，读取始终服从对象持久化的布局。

## 正确性标准

1. CLI 和 YAML 均接受 `auto`，CLI 优先；默认不发 hint；feature 关闭和非 S3 后端拒绝启用。
2. 0、64 KiB、256 KiB、1 MiB 前后 1 byte、4 MiB 前后 1 byte、MPU 和大对象之后的小尾块，实际 HTTP 请求元数据与规则一致。
3. 正常上传、重试、vectored 与 create-only 的请求字节完全一致；MPU 元数据只在创建时发送，重组所有 part 后字节一致。
4. 经真实 BrewFS 编码器的 LZ4、Zstd 及不压缩块，按编码后大小选择。包含 1 MiB 减 4 bytes 和减 3 bytes 的逻辑块，以检查 4-byte 格式头边界。
5. 在 ACS 的真实 RustFS 上检查 HEAD 返回的实际 EC 块大小，完整 GET 校验所有字节；再以 Redis + FUSE 验证后台上传、清债和重挂读取。服务端关闭 hint 时另测降级。
6. 默认和启用 feature 的工作区 lib/bin 测试、编译、clippy 和格式检查通过后，才接受实现。已知无关 all-features 基线失败单独保留，不宣称消除。

## 更广泛的性能实验设计

FUSE 文件尺寸至少包括 4 KiB、64 KiB、256 KiB、1 MiB、4 MiB、4 MiB + 64 KiB、16 MiB、64 MiB；另加格式边界正确性样本。每个文件尺寸都交叉无 hint、固定 1 MiB、固定 4 MiB、auto，保留固定 64/256 KiB 作为完整机制对照；不使用一个文件尺寸代表所有文件。

固定 BrewFS 4 MiB 数据块，分别测试不压缩的不可压缩数据和明确压缩率的 LZ4 数据。记录每个实际上传对象大小、EC 布局、PUT 数和完整 GET 覆盖范围。64 MiB 文件通常产生多个对象；按文件大小与实际对象分布分别展示，避免混为一谈。

主项目为完整文件写入及完整读取，包含冷 BrewFS 缓存和暖缓存、并发 1/4、后台上传模式及同步对照。写入同时报告应用阶段和上传全部完成的总耗时；必须确认 dirty/pending/inflight 清零，重新挂载后校验哈希。不得以 SSD 暂存速度替代远端持久化吞吐。

完整文件读取也要记录底层请求形态：FUSE/内核可能拆分读取，BrewFS 的缓存和预取设置又会影响最终 HTTP GET/Range。按实际覆盖的字节、请求数和下载放大报告。整块联动优化另保留固定 1 MiB EC 的对照，用来区分请求合并、缓存准入和较大 EC 块的贡献。

先做正确性和四轮机制筛选，再冻结九轮性能实验；相同主机、资源、数据、缓存设置和运行顺序。吞吐比的 95% 区间下界 ≥ 0.95，p95 延迟比区间上界 ≤ 1.05 为无明显回退门槛；明确收益要求吞吐几何均值 ≥ 1.05 且区间下界 > 1。保留失败、慢请求及不利结果，不拼接不同环境的历史样本。

报告必须列明文件大小、实际 S3 对象大小、测试标准、原方案与新方案的绝对吞吐/延迟、变化及区间，并画不同文件大小的整写/整读对比图。当前实现和正确性验证不等同于已完成性能验收。

## 2026-10-19 写入、真实缓存热读与 auto 修正

本轮起点为 BrewFS `e5fec716503817917a5d47abd62a1986ffedec38` 加 RustFS `cc4926fac1107aee76540f28bf22dbd47fcbca24`。RustFS 源码未改；复用已有 release 二进制。所有运行验证在杭州 ACS，WSL 仅编译。客户端 4 CPU / 8 GiB，RustFS 8 CPU / 16 GiB、四块独立 40 GiB ESSD PL1、2+2 EC，Redis 独立部署。BrewFS 数据块 4 MiB、读写内存预算各 64 MiB、写暂存 1 GiB，不压缩。

### FUSE 请求和对象边界

实际探测中，4 MiB 应用写入可以生成一次 4 MiB FUSE WRITE；完整读取通常拆成 128 KiB FUSE READ。128 KiB 应用小写入仍能聚合成 4 MiB S3 数据对象。ACS 实际 BDI read-ahead 为 128 KiB，`/sys` 只读；实验没有强改内核设置。

因此请求大小与分块能够配合，但不能把一次 FUSE 请求等同于一次对象请求。读取沿用完整 GET 合并及 LRU，让多个 FUSE 片段复用同一块；auto 继续使用加格式头、压缩后的最终上传对象长度，不使用请求长度、整个文件长度或 SSD 预分配量。

### 本轮实现

- 已提交且远端上传完成的 slice 立即释放数据页及写预算，消除约两秒的 recent-slice 保留对后续写入的阻塞。尚未上传完成的数据仍供本地覆盖读取及恢复使用。
- 对已经缓存、元数据已知、完全落在单个数据块内的读取，FUSE 回复共享不可变 `Bytes`。脏数据覆盖时再复制；空洞、跨块和未命中继续使用正常读取路径。workspace provider 保留既有请求 fence 与输出所有权流程。
- auto 对编码后不超过 1 MiB 的对象省略 hint，较大对象选择 1 MiB EC。同一入口覆盖普通、vectored、create-only、MPU、恢复上传和重试，固定 hint 配置不变。

### 实验阶段与标准

第一阶段 184 组以相同旧 auto（4 MiB EC）隔离写入与共享回复改动，并保留原始无 hint 组合和固定 1 MiB 控制。真实缓存热读另做 64 组；最终 auto 修正后执行 3 组布局检查和 88 组四轮确认。各阶段独立统计，不拼接轮次，不把倍率相乘，不重复运行原始无 hint 基线。

最终确认覆盖 1 MiB、4 MiB、4 MiB+64 KiB、16 MiB、64 MiB 文件，各并发 1/4，另加 4 MiB 整文件混合读写。4/64/256 KiB 的提示规则未改，保留第一阶段结果。每个对照按四轮配对吞吐几何平均计算，枚举 256 个自助样本得到 95% 区间。明确收益要求比值至少 1.05 且下界大于 1；完整无明显回退门槛要求吞吐比下界至少 0.95、文件 p95 比上界至多 1.05。

写入主指标计至远端上传完成，另报告应用阶段和全部 dirty/pending/inflight 清零的耗时，避免把成本移到后台。所有组检查完整文件 SHA-256、四盘 EC 布局、清债及卸载。冷读只清空客户端缓存，保留服务器和云盘缓存。

| 最终确认，相对已交付版本 | 吞吐结果 | 完整门槛 |
|---|---|---|
| 1–64 MiB 整文件写入 | 10/10 明确提升，1.838–2.722 倍 | 10/10 通过；全部清债口径也改善 |
| 空客户端缓存整文件读取 | 5/10 明确提升；全部比值范围 0.969–1.126 | 6/10 通过，4/10 未通过，未观察到区间支持的明确回退 |

冷读未通过的场景为 1 MiB/并发 4、4 MiB/并发 1、16 MiB/并发 4、64 MiB/并发 1；普通内核热读未通过为 16 MiB/并发 4、64 MiB/并发 1 和 4。未通过仍按原门槛保留，不宣称普遍无回退。

单独的 64 组真实缓存热读关闭跨 open 的 KEEP_CACHE，用 32 MiB 工作集放入 64 MiB 缓存。每次重复读取均有实际 FUSE READ，且没有新增 S3 GET。两边均包含写预算修复，仅隔离共享回复：8/8 通过完整门槛，6/8 明确提升；1 MiB 文件并发 1/4 提升 10.8%/12.4%，4 MiB 为 17.3%/16.8%，16 MiB 为 20.0%/15.5%，64 KiB 约 0.9%，基本持平。最终 auto 修改没有改变这些读路径和已解码缓存字节，七个相关源文件逐字节一致。

普通重复读取的第一阶段所有汇总单元均无 FUSE READ、无 S3 GET；它测的是内核页缓存，不能用于证明 BrewFS 缓存代码收益。更早仅绕过任务调度的候选约 1% 变化，已撤回并保留记录。

### auto 修正的依据和边界

第一阶段相同新客户端、相同 RustFS，只改变 EC 提示的对照中，旧 auto 4 MiB 相对固定 1 MiB 没有明确读写吞吐收益；4 MiB+64 KiB/并发 4 冷读比值为 0.901，95% 区间 [0.874, 0.925]。两边每轮均为 2176 次 FUSE READ 和 128 次 S3 GET。此结果否定了“EC 分段更少必然更快”，成为保留 1 MiB 的依据。

最终策略明确请求 1 MiB，这在本轮 RustFS 默认布局下与默认 EC 大小一致；启用 hint 的挂载同时保留完整 GET 合并和缓存联动。因此整体收益不能归因于“hint 数值变大”。第一阶段对原始无 hint 组合的必要补测中，六个写入场景为 1.781–2.636 倍，六个冷读场景为 1.574–3.455 倍，全部通过；这些是旧 auto 阶段的组合结果，不改称最终策略与原始版本的直接对照。

### 环境边界和未完成项目

8 vCPU 构建 Pod 的设备白名单不允许打开 `/dev/fuse`；已成功的 1 vCPU Pod 允许打开，两者实际权限不同。其 5.10 内核又不支持默认 io_uring 运行时要求的同步取消，故实际挂载采用已有 Tokio 运行时。这些启动失败记录保留，不能解释为成功的性能样本。新部署必须在实际 Pod 上重新确认 FUSE 能力。

本次 RustFS 四个纠删码目录共用临时盘，并显式使用 `RUSTFS_UNSAFE_BYPASS_DISK_CHECK=true` 的测试开关，仅验证编码、上传与读取正确性。未验证独立磁盘的容错和存储性能。正式性能实验还需冻结合适的独立盘拓扑、资源规格、release 构建、运行顺序与缓存控制，然后执行上面的整文件/整对象对照；本表没有吞吐提升结论。
