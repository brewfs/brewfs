# 百万文件热随机读写实验设计 v1

状态：**方案已定义，尚未执行**。本文件与 [参数表](entity-packed-hot-random-v1/plan.json)
定义下一轮实验；运行驱动、有效缓存参数和构建版本仍需在执行前验证并冻结。
2026-11-01 的 [原始报告](entity-packed-million-r2.md)、冻结驱动、失败记录和费用保持原样。

## 这次改变什么

从每个性能单元中删除重复的百万文件全目录遍历；将完整命名空间验收改为每次发布数据集后、
每个产品各做一次的独立阶段。每次读写的内容校验、工作区隔离、持久化、强排空、普通卸载
和真实进程退出仍是必需检查。

上一轮完整遍历已经在生命周期计时之外。BrewFS 每单元的额外校验耗时
2004–2009 秒；取消重复执行能缩短实验并降低资源开销，不会改变已经测得的随机读写延迟。
新的端到端账本仍包含一次导入、一次完整验收、首次读取、预热、首次 COW、稳态读写、
校验、排空、退出、故障等待、采集和归档。

本轮要回答三个问题：已验证数据真正留在客户端缓存后，随机读的成本是多少；已经拥有
upper 数据的文件再次覆盖写有多快；同样每次写都 fsync 时，混合读写能否持续完成。
快速创建工作区作为单独结果保留，热读写结果不包含 clone 时间。

## 当前实现的前置条件

检查基于上一轮实际测量的 BrewFS 代码 `918deb90e046889d94eb8ff633822e275792ce28`：

- [entity FUSE](../../src/fuse/entity.rs) 的 `open` / `create` 返回 `FOPEN_DIRECT_IO`。
  [配置解析](../../src/config.rs) 拒绝 entity 挂载的 `fuse.keep_cache=true`。
  仅从应用打开标志中去掉 `O_DIRECT`，不会使这条路径获得内核数据页缓存。
- [packed lower memo](../../src/workspace_overlay/entity/packed_lower_cache.rs)
  保存不可变元数据，不保存文件内容。
  [packed pipeline](../../src/workspace_overlay/packed_v3/wire005/pipeline.rs)
  合并在途请求，不保留已完成的数据作为 payload cache。
- 普通 VFS 的块缓存配置不能直接当作 entity packed 路径的缓存支持。
  旧 JuiceFS 挂载辅助函数在同步模式还会固定 `cache-size=0`；下一轮需验证实际生效值，
  不能只给旧函数传入一个正数就宣布缓存打开。

因此，**真实客户端热数据实验需要先有可验证的 entity 数据缓存支持**。
本方案优先采用有容量上限的客户端数据缓存，继续使用 direct I/O，避免把 Linux 页缓存
结果误归因于文件系统数据路径。普通 buffered/page-cache 实验另立方案。

实现前置条件为：首次填充验证内容；只复用已验证的不可变数据；缓存身份覆盖后端、
manifest/绑定、对象/帧版本及读取范围；upper 覆盖写后通过当前已提交版本选取数据；
租约、权限、版本与绑定检查仍生效；错误不进入成功缓存；容量、淘汰和关闭均有边界。
新版本必须先通过这些正确性用例及仓库规定的代码检查。本文件不修改运行时。
若使用主线已有的新实现，也需记录确切提交和这些路径的实际行为。

后续缓存候选位于 `codex/entity-payload-cache`，基于主线
`85fe85e6eb1e8c83d509a29d84f82b67ee32a1e8`。通过
`--entity-read-cache-bytes 536870912` 将共享 lower / upper 的保留数据预算固定为
512 MiB；这是该实验性 packed entity 挂载的默认值，设为 `0` 可关闭。
实现与计数口径见 [entity 数据缓存](../architecture/read-path.md)。
其 lower 缓存保存实际读取并认证的范围，upper 缓存保存认证过的不可变对象；
每项另计 512 字节管理费用。该候选不是上一轮测量所用版本，也没有新的性能结果。
运行驱动和候选提交仍需在正确性与仓库检查完成后冻结。

后续 `codex/entity-packed-frame-cache` 将 lower 的保留单位改为完整的已认证、已解码帧。
读取帧内另一个文件或不同范围可以共享已取回的数据，upper 与 lower 仍共用上述预算。
这不增加后台预取请求；每次缺失后的实际填充仍校验返回字节，不能用历史验证记录替代。
lower 命中计数改按帧查询统计，实验驱动还需单独统计完整 I/O 命中率。
该改动没有新的百万文件吞吐量结果，正式实验仍需冻结实际提交和有效参数。

## 数据、资源和配对

| 项目 | 预设 |
| --- | --- |
| 底层数据集 | 1,000,000 个 4 KiB 文件、1024 个目录，沿用原确定性内容规则 |
| 导入 | 每个产品一次；BrewFS producer 的临时 SQLite 明确放在数据盘，计入导入时间 |
| 后端 | 分离的客户端 / RustFS / TiKV；同 AZ、相同硬件与资源限制；记录实际版本 |
| 持久化 | 同步 `upload_before_commit`；每次覆盖写后 `fsync` |
| 格式 | raw，无压缩，4 MiB chunk/block，packed inline 关闭、256 KiB random-frame cap |
| 并发 | 8 个应用 worker、同样的运行时/上传并发；一次只测一个产品 |
| 缓存 | 每个活动客户端 512 MiB 保留数据缓存、0 SSD clean cache；预取/预读关闭 |
| 资源上限 | 每个产品的活动客户端与工作负载合计 8 CPU / 8 GiB；记录实际 RSS、cgroup 和缓存占用 |
| 元数据缓存 | 记录两边支持的配置及一致性语义；采用公开的常规配置，不沿用仅把 JuiceFS 缓存归零的设置 |
| 重复 | 3 轮操作配对，顺序 BF/JF、JF/BF、BF/JF；每单元 4 个新工作区，共 24 个 |
| 工作区使用 | 依次执行；BF 独立工作区挂载，JF native clone；每个工作区使用独立冷缓存域 |
| 热集 | w0/w1：1024 文件 = 4 MiB；w2/w3：16384 文件 = 64 MiB |
| 选取 | 从整个百万文件集合均匀选取；seed 9173；两产品相同，执行前保存文件列表和 trace SHA-256 |

4 MiB 热集沿用上一轮 1024 文件的规模，作为主场景。64 MiB 是预先声明的容量敏感性场景，
两个规模均完整报告。逻辑热集大小不等于缓存驻留开销：4 KiB 读取可能要求缓存整个 packed
frame。记录实际驻留字节、帧数和淘汰量；64 MiB 场景未达到热命中门槛时，标记为
“预热后有淘汰”，保留两边结果和原因，不改热集来挑选更快的结果。

每轮重复使用同一个已导入 base，属于操作重复，不是三次独立部署。4 个工作区是单元内
子样本。按轮和热集规模分别计算配对结果，避免把每一次 I/O 当作独立实验重复。

## 每个工作区的固定执行顺序

1. **创建工作区。** 计时 mount/bootstrap 或 native clone，记录到可用的时刻。
2. **填充与预热。** 对完整热集做两遍确定性随机排列读取，逐字节验证；两遍分别计时。
   预热后保持挂载与缓存，不再跑全目录扫描。被测操作和预热使用相同的 open/read/close 路径。
3. **热随机读。** 65536 次均匀随机 4 KiB 读取，8 worker，每次 open/pread/close。
   记录 syscall 延迟和应用完成延迟；每次返回的字节都与确定性期望值比较。
4. **首次 COW。** 从热集中固定选 256 个文件，各修改一次并 fsync；使用工作区专属内容。
   这一阶段独立计时，所有对象远端可读后进入重复写阶段。首次 COW 不记作热覆盖写。
5. **upper 预热。** 对这 256 个已提交文件做两遍读与字节验证，单列时间与缓存证据。
6. **热随机覆盖写。** 在这 256 个文件上做 2048 次随机 4 KiB 覆盖，每次
   open/pwrite/fsync/close。每次都有不同、可重建的内容版本；所有 fsync 等待均计时。
7. **upper 再预热。** 读取这 256 个文件的最终版本两遍，单列时间。
8. **热混合读写。** 同一 256 文件集合，8192 次操作：6144 读、2048 写。
   每次写仍 fsync；按 worker 预生成精确 3:1 比例与顺序，避免不同执行速度改变读写比例。
9. **关闭与独立检查。** 强排空、普通卸载、真实退出；用隔离的冷缓存验证器验证最终内容、
   所有修改过的路径、base 未改变和跨工作区隔离。完成检查后才能关闭该单元。

每个文件只归属一个 worker，该 worker 对其读写串行执行。每个 worker 持有 32 个可写文件，
避免数据竞争令期望内容不确定。该场景覆盖独立文件并发，不代表多线程争用同一文件。
被测单元共享相同的操作列表和每文件版本演进；真实调度顺序单独记录。

覆盖写总数为每工作区 256 + 2048 + 2048 = 4352 次，24 工作区共 104448 次。
热读阶段加混合读共 71680 次/工作区，合计 1720320 次；预热和最终验收另计。
这些是计划操作量，不是已有运行结果。

## 热状态如何确认

先在小规模本地验证路径和计数，再冻结下一轮运行驱动。下列事实需要同时存在：

- 实际命令、有效配置和运行时计数证明数据缓存接入了被测路径，并有 512 MiB 上限。
- 对固定 4 MiB 热集完成预定两遍预热后，探针读取的**完整数据缓存命中率至少 99%**。
  lower 和已经写入 upper 的集合分别检查；元数据命中不代替数据命中。
- 客户端命中/缺失/淘汰计数与独立对象请求日志相符，能区分 payload 与 metadata 请求。
  服务器页缓存使远端 GET 更快，不算客户端数据缓存命中。
- 正常覆盖写后立即读取本版本、隔离工作区读取旧版本，以及冷挂载读取最终版本都正确。

预热遍数固定。主场景达不到门槛时，保留诊断结果并先解决实现或容量问题；不反复预热直到
出现好看的时间。正式测量期间再次记录命中比例；热状态失效的样本按实际状态报告。
未来候选版本与自己的 cache-off 消融必须使用同一 trace、并发和持久化语义，作为单独
诊断；旧半预热数据不能直接当作这轮热缓存提升倍数的分母。

## 精简校验后的覆盖范围

| 检查 | 新频率与归属 |
| --- | --- |
| 百万文件名称、目录、数量 | 每产品每次 base 导入后完整检查一次，独立记账；随后重置客户端缓存 |
| 随机读字节 | 所有被测读与预热读均检查；记录校验 CPU 和驱动墙钟成本 |
| 写后内容 | 每次写的期望版本可重建；阶段结束检查全部 256 个文件，错误立即记录 |
| 跨工作区/base 隔离 | 检查全部修改过的路径在本工作区、base 和保留工作区中的各自期望版本 |
| 未修改路径 | 每个工作区固定抽查 1024 个不在修改集合内的路径及内容 |
| 远端持久化 | 强排空后使用独立冷客户端读取全部修改文件；保留对象提交与校验凭证 |
| 债务和退出 | 每单元保存零上传债务、普通卸载、真实 worker 退出以及无遗留进程的证据 |
| 全局 POSIX/命名空间操作 | 使用独立正确性套件；本负载只有读取和定长覆盖，不覆盖 rename/unlink 等操作 |

一次 base 验收加上述工作区检查，替代的是“每轮重复扫整个 base 和每个 clone”的覆盖范围。
报告明确列出这一变化。原始百万文件测试的完整遍历性能仍是已有结果。

## 计时与报告

主指标分别是热随机读 IOPS/P50/P95/P99、热覆盖写持久完成 IOPS/P95/P99、
混合读写的读延迟与持久写延迟。写操作延迟包含 pwrite 与 fsync，阶段完成时间包含
正常关闭和排空。记录以下四种时间，分别汇总：

1. syscall 的 open、read/write、fsync、close 延迟，以及一个应用操作的合计延迟。
2. 活动阶段墙钟，包括驱动调度与字节检查；不以各 worker 时间之和代替墙钟。
3. 工作区从创建、预热、首次 COW 到全部热阶段、检查、排空、退出的端到端时间。
4. 完整活动从准备、一次导入和验收到资源释放的时间与费用，包含所有等待和中断。

驱动采用可校准的原生 I/O worker 和有界记录缓冲，避免 Python GIL 或逐操作落盘成为
热缓存吞吐上限。提前在相同驱动下核对计时/内容验证的开销；原始延迟、错误和计数全部保留。
读取内容的检查在 syscall 计时外，但计入应用完成与阶段墙钟。

每阶段同时给出 CPU、客户端内存、TiKV 事务/RPC、对象 GET/PUT 次数与字节、缓存驻留和
命中/淘汰、上传债务。首次填充、预热和 COW 的代价与热阶段并列展示。BrewFS 比 JuiceFS
更快的判定依据是相同场景的实际配对结果；创建加速、读加速、持久写加速各自归因。

保存三轮逐轮结果及范围；仅三个操作重复时不宣称普遍统计优势。失败、慢阶段和恢复数据
保留；恢复单元不计作无中断性能配对。观测连续性要求和正确性门槛在执行前固定。
