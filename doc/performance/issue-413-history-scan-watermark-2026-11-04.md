# 历史扫描去重（watermark）实验：证伪

## 结论先说

历史扫描的重复率确实很高（**92.5%**），但「按 chunk 记水位线、只扫新增区间」的实现
**没有降低 close 尾部，反而从 5.68 s 退到 10.9 s**。两次干净轮次结果一致
（10.981 s / ~10.9 s），不是噪声，也不是 debug 观测开销。

**成本被挪位置了，没有被消除** —— 与「lateclaim512」那次失败模式相同。

## 起点：扫描普查（可复用的硬数据）

同一份 60 s 受压（4 jobs × depth 32 × 4 KiB randwrite，direct=1）的 2,000 次扫描：

| 项 | 数值 |
|---|---:|
| 扫描次数 | 2,000 |
| **空扫**（扫了没结果） | **1,033（52%）** |
| 非空扫描 | 967 |
| chunk layer 数 | 66 |
| 扫描行数总计 | **693,451** |
| **其中重复行** | **641,759（92.5%）** |
| 唯一行 | 51,692 |
| 每次非空扫描行数（mean / median / max） | 717 / 687 / 1,677 |
| 单个 chunk layer 被扫次数 | **31–36 次** |

⇒ 理论上扫描量可降到 7.5%，这也是当初判断「去重能省 14 秒」的依据。

## 实现（已回退，补丁保留）

`ExtentWatermarkCache`：`BTreeMap<(layer_id, chunk_id), ExtentChunkWatermark>`，
每个 chunk 记录已扫区间集合 `Vec<(u64, u64)>`，只扫新增区间；水位线内存受
`V3MountBudget` permit 约束；从 `generation: &[KvCheck]` 快照构造以避免读到过期数据。

改动规模：6 文件 +583/−16。补丁：
`/mnt/brewfs-data/home/hxy/issue413/history-scan-followup/watermark-implementation.patch`

## 测量（无观测、与 prefix512 同口径）

| 指标 | prefix512（此前最优） | watermark64-p1 | watermark64-p2 |
|---|---:|---:|---:|
| **活跃结束→严格排空** | **5.68 s** | **10.98 s** | **~10.9 s** |
| close/tool 尾部 | 3.82 s | 9.03 s | 8.74 s |
| 严格排空（fio 返回后） | 1.68 s | 1.80 s | 1.71 s |
| 写带宽 | 3.558 MiB/s | 3.716 | 3.626 |
| 有效带宽（含 close/排空） | 3.251 MiB/s | 3.141 | 3.082 |
| RSS 峰值 | 244.75 MiB | 318.3 | 309.1 |
| p50/p99 vs baseline | p99 304 ms（−73%） | p99 比 784 基线 −64.4% | 同 |
| 9 项门 | 8 过 | 8 过（同一项失败） | 8 过 |

**活跃带宽与 p99 反而略好，但 close 尾部接近翻倍、RSS 也更差** ⇒ 收益与代价错位。

## 为什么会失败（推断，未逐项验证）

1. **区间合并成本**：每次追加都要与已有区间做合并/去重（`merge_watermark_ranges`），
   随机写产生的区间高度碎片化 ⇒ 合并本身成为新开销。
2. **permit 申请过频**：`admit_watermark_ranges` 按区间条数申请，碎片化后申请次数上升。
3. **扫描并没有真正减少**：单次扫描 717 行的主体可能不是「历史全量」而是
   「本批新增 + 必要的相邻上下文」；去掉重复行后仍未触及主要成本。

⇒ 若要再试，应先做「扫描行里有多少是必要上下文」的第二次普查，而不是直接上水位线。

## 保留什么

- 普查数据（92.5% 重复 / 52% 空扫 / 每 layer 31–36 次）作为后续优化的依据
- watermark 实现补丁（未合入，供参考）
- **prefix512 仍是当前最优**（close 尾部 5.68 s）

## 未验证

- 未验证「减少重复扫描但保留上下文」的变体
- 未做「扫描行必要性」的二次普查
